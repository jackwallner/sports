## What survived, ranked

1. **Bug 1, offline cached briefing shows no age.** Most users reached (anyone opening offline after a day), every time it happens, and the cost is quoting stale news, the core promise.
2. **Bug 2, server errors labelled Offline.** All cached users at once, only during backend incidents; it also routes them into bug 1. Fix with bug 1 (carry the failure kind and the row's age into the state).
3. **Bug 5, rating prompt after a purchase.** Narrow route, but a real customer can hit it in production.

Unverified, in the order to settle them: bug 3 (one device run), then bug 4 (Test Store UI test).

## Product calls

1. Pro "fresher briefings" not gated: agree. Cocktail Party is regenerated at the same three cron slots as the paid rooms (`20261013000000_pg_cron_pipeline.sql:41-49`), so the paywall benefit "Fresh stories morning, midday, and evening" (`PaywallView.swift:198`) is not a difference between tiers. Worth a copy decision before App Review reads it as a misleading benefit.
2. Refresh-limit machine unreachable: agree. The only `viewModel.refresh()` caller is Settings' Manual refresh, gated on `isPro` (`SettingsView.swift:69-75`, `TodayBriefingView.swift:208`).
3. Paid rooms client-gated only: agree, `using (true)` for `anon` (`20260516214000_initial_sideline_schema.sql:135-139`), no later policy change.
4. Room link leaves `pendingDeckCard`: agree, no shipping control produces `sideline://` links (only `TodayBriefingView.swift` and `.claude/rules/iphone-duo.md` mention them).
5. Static "Next refresh" hint: **disagree, this is a customer-visible bug**, CONFIRMED by code. Windows are UTC hours (`generate-briefings/index.ts:264-273`, cron 14:05, 19:05, 23:05 UTC) and the hint is fixed per window (`Briefing.swift:14-21`). A Pro user in London reads the 14:05 UTC "morning" row at 2 pm with "Next refresh midday" while the next run is 7 pm; Europe and Asia are wrong every day, and during an outage every Pro user sees a confident next-refresh time beside "Double-check before quoting". Route: any Pro user, online, footer (`FreshnessFooter.swift:41-44`). Rank it after bug 5: Pro only, copy only.
6. Offering choice ignores `current`: agree, documented at `StoreService.swift:175-178`.

No other serious state bug turned up inside the audit's scope. The "Ruled out" items checked hold (`loadGeneration` guard, rooms-card clamp at `BriefingDeck.swift:126-128`, Ask to Buy mapping).

## Method changes

- **Read third-party behaviour before claiming a timing window.** Bug 4's route rests on `isPro` arriving late on cold launch; RevenueCat's delegate setter delivers cached CustomerInfo at once. A grep of the SDK would have refuted the route and the lifetime-owner cost.
- **Quote a citation with its surrounding comment, and check its scope.** Bug 3 cites a cooldown doc that says the opposite of the claim ("paces our calls"); bug 4 cites a Settings-row comment as an app-wide rule.
- **Drive tests with the exact calls the view makes.** SM1 passes `storedPersona: .dateNight`, which no route produces; the UI route goes through `roomAwaitingUnlock`. It fails the same way here, but only by luck.
- **Describe the full rendered symptom.** Bug 1 missed the amber tint and the duplicated banner; the claim was still right, but "no stale warning" overstates it.
- **Name the OS assumption behind a code path and mark it unverified.** Bug 3 depends on background task and review-prompt behaviour that the code cannot show, and the app has no non-demo headless path to it.
- **Probe the breadth of a confirmed branch.** Bug 2 was shown for a 503 only; the same branch covers empty results and decode failures, which matter more given the iOS 17/18 decode history.
